# try_3_code — движок перебора клеточных автоматов

Рабочая реализация требований из `try_3_plans`: описание эксперимента отдельно
от исполнения, явные интерфейсы модулей, numba-ядра, параллельный перебор,
сохранение успешных конфигов вместе с настройками и визуализация кадров.

## Установка

Нужны Python ≥ 3.11, `numpy` и `numba`.

```bash
python -m venv .venv
.venv/bin/pip install -r requirements.txt
```

Пакет не требует установки: все команды запускаются из корня `try_3_code`.

```bash
cd try_3_code
../.venv/bin/python -m sweep --help
```

## Быстрый старт

```bash
# карта осей и размер пространства
python -m sweep space -e rings_rot --count --limit 5000

# модули, требования и фазы эксперимента
python -m sweep modules -e rings_rot

# случайный перебор 1000 конфигов в 4 процесса
python -m sweep run -e rings_rot --strategy random --limit 1000 \
    --mode process --workers 4 --seed 1 --out runs/rings

# муравей Ленгтона: 22 набора правил × инициализации × число муравьёв
python -m sweep run -e langton --strategy random --limit 800 \
    --mode process --workers 4 --seed 1 --out runs/langton

# остановиться, как только найдено 200 успехов
python -m sweep run -e life --strategy random --until 200 \
    --mode process --workers 8 --out runs/life

# продолжить прерванный прогон (готовые конфиги пропускаются)
python -m sweep run -e life --strategy random --until 200 \
    --mode process --workers 8 --out runs/life --resume

# посмотреть успехи
python -m sweep show --run-dir runs/life

# лабиринты: растущие стены, плотность 30–80%, связные проходы
python -m sweep run -e maze --strategy random --limit 1500 \
    --mode process --workers 4 --seed 3 --out runs/maze

# лабиринт с окном 9×9: механизмы, изменения карты ≤ 10%, графовый фильтр
python -m sweep run -e maze9 --strategy random --limit 1200 \
    --mode process --workers 4 --seed 5 --out runs/maze9

# открыть галерею всех прогонов: переключатель экспериментов и страницы;
# кадры собираются из конфига на лету, мета-параметры можно менять
python -m sweep view --runs runs --port 8000

# статическая галерея для GitHub Pages: автоматы считаются в браузере;
# каталог сборки в git не попадает (см. pages/README.md)
pages/build.sh /tmp/sweep-site

# по желанию — экспорт PNG/HTML (по умолчанию в ./viz, каталог прогона не трогается)
python -m sweep viz --run-dir runs/life --index 0 --out viz
python -m sweep live --run-dir runs/life --index 0 --fps 8
```

`Ctrl+C` прерывает прогон: работники завершают текущий тест, уже записанные
результаты остаются на диске, повторный запуск с `--resume` продолжит с места
остановки.

## Слои

| Слой | Модуль | Ответственность |
|---|---|---|
| описание | `sweep/experiment.py` | оси, выбранные модули, фазы, фильтры |
| перебор | `sweep/space.py`, `domains.py`, `handles.py` | зависимые оси, ограничения, стратегии |
| интерфейсы | `sweep/interfaces.py`, `module.py` | `Capability` / `Requirement`, роли модулей |
| сборка | `sweep/assembly.py` | проверка совместимости и построение рантайма |
| исполнение | `sweep/runtime.py` | один тест: инициализация, фазы, метрики, фильтры |
| параллельность | `sweep/parallel.py` | serial / thread / process, отмена, прогресс |
| хранение | `sweep/storage.py` | `successes.jsonl`, `summary.json` |
| визуализация | `sweep/visualize/` | общий интерфейс, PNG/HTML, терминал |
| эксперименты | `sweep/experiments/` | `life`, `rings_rot`, `cyclic_waves`, `langton`, `maze`, `maze9`, `omega5`, `omega5_dense` |

Ключевые правила:

* конфиг — только скаляры и `seed`; массивы и numba-объекты создаются заново;
* прогон хранит только конфиги и метрики: кадры и картинки не сохраняются, их
  пересобирает `sweep/replay.py` из того же конфига; kernel компилируется один
  раз на эксперимент, а не на конфиг;
* несовместимые пары «данные × правило» отсекаются до итераций;
* итерация пишется прямо в файле эксперимента и передаётся в
  `experiment.iterate(...)`;
* визуализатор эксперимента — отдельный класс за общим интерфейсом.

## Файлы прогона

```
runs/<name>/
  successes.jsonl   только успешные конфиги
  summary.json      счётчики и параметры запуска
```

Отбракованные и остановленные тесты на диск не пишутся: их всего лишь
счётчики в `summary.json`. Поэтому `--resume` пропускает уже найденные
успехи и заново проверяет всё остальное — для перебора это дешевле, чем
хранить миллионы строк.

Других файлов прогон не создаёт. Запись в `successes.jsonl` — одновременно
результат отбора и рецепт автомата: по `config` и `seed` его собирают заново
(`sweep/replay.py`), поэтому `view`, `viz` и `live` показывают свежее
исполнение, а не сохранённые картинки.

## Муравей Ленгтона (`langton`)

Мир — это сетка следа: клетка хранит номер цвета (правило), муравей читает
цвет, поворачивается по таблице правил, сдвигает цвет на единицу и делает шаг.
Курс — одно из восьми направлений, поэтому повороты бывают на 45°, 90° и 180°:

| символ | поворот |
|---|---|
| `L` / `R` | 90° влево / вправо |
| `l` / `r` | 45° влево / вправо |
| `b` | 180° |
| `?` | случайный поворот из этого набора (выбирается по `seed`) |

Что перебирается:

* наборы правил (`rule.langton.rules`): 2 правила `LR`/`RL`, 4 правила на
  ±45°/±90°, 6 правил с двумя поворотами на 180° и 7 правил с одним случайным
  поворотом — всего 22 набора;
* число муравьёв `rule.langton.ants` (1, 2, 4, 8) и старт `rule.langton.place`
  (`center` или `random`);
* инициализация следа `trail.init`: `empty`, `random_light` (15% цветных
  клеток), `random_dense` (30%);
* размер сетки `grid2d.size` (96 или 128, границы заворачиваются — тор);
* длительности фаз `phase.warmup` (500…1500) и `phase.observe` (3000…4500).

След хранится в одной int32-сетке: `0` — клетка не посещалась, `1..colors` —
цвет следа, `colors+1..2*colors` — тот же цвет плюс отметка муравья
(`colors` = число правил). Сами муравьи живут в рантайме правила, поэтому
конфиг остаётся скалярным и повторная сборка с тем же `seed` даёт тот же след.

Отбор начинается после прогрева: проверки идут каждые 100 итераций, но решают
последние 300 шагов фазы — муравью нужно время «расцвести».

* `filter.ant_settle` — след перестал расти (муравей зациклился в своём следе,
  а не уходит бесконечной магистралью): прирост ≤ 0.2 клетки за шаг; закрашенное
  целиком поле отбрасывается как `saturated` — у него и рост, и симметрия
  выполняются тривиально;
* `filter.ant_pattern` — финальный след симметричен (совпадает с отражением
  или поворотом, IoU ≥ 0.55).

На прогоне из 3200 случайных конфигов проходит около 3% — как раз интересные
автоматы. В галерее `phase.observe` можно поднять до 20000 и посмотреть, что
муравей делает дальше.

## Лабиринт (`maze`)

Сетка из двух состояний: `0` — проход, `1` — стена. Из редкой случайной
затравки стены растут: клетка-проход становится стеной, если соседей-стен в
окне ровно `born_lo..born_hi` (обычно 1–2 — тогда сеть растёт деревом, а не
пятнами), и только с вероятностью `rate` за шаг. Стена выживает, если её
соседей `surv_lo..surv_hi`, иначе прорастает проходом.

Что перебирается:

* `grid2d.size` — 64, 96 или 128;
* `maze.fill.density` — плотность затравки (3%, 6%, 12%);
* окрестность — квадрат Мура или диск с метрикой
  Чебышёва/Евклида/Манхэттена, радиус 1–2: форма и толщина стен;
* `rule.maze.born_lo/hi`, `surv_lo/hi` — топология сети: дерево (1 сосед),
  кольца (2), пятна (3);
* `rule.maze.rate` — скорость роста и итоговая плотность сети;
* `wrap` окрестности и `rule.maze.border` — тор или замкнутый рамкой лабиринт;
* `phase.observe` — 180–300 шагов роста.

Отбор:

* `filter.density` — стен 30–75% (значит, и проходов не меньше 25%);
* `filter.maze_structure` — в каждой из 8×8 плиток плотность проходов 30–80%
  (`local_dense` / `local_sparse`); все проходы — одна связная система по
  4-соседству (`broken_passages`); средний размер компоненты стен не меньше
  1.6 клетки (`dusty_walls`, отсекает пыль из одиночных стен).

Связность проходов считается по 4-соседству: через диагональ пройти нельзя,
поэтому сито из одиночных стен сразу даёт сотни изолированных карманов —
именно так отсекаются «шумные» правила.

## Лабиринт с окном 9×9 (`maze9`)

Тот же рост стен, но решение принимается по подмаске окна 9×9 (радиус 4,
80 соседей). Механизм задаёт, что именно «видит» растущая стена:

| механизм | подмаска | что даёт |
|---|---|---|
| `inner` | кольцо 3×3 | ветвистое дерево, плотная застройка |
| `middle` | кольцо 5×5 без 3×3 | петли среднего масштаба |
| `outer` | кольцо 9×9 без 5×5 | широкие проходы, стены на расстоянии |
| `rim` | край окна (радиус 4) | длинные прямые участки |
| `cross` | четыре луча | крестообразные элементы |
| `diagonals` | четыре диагонали | диагональные стенки |
| `corners` | четыре угловых блока 3×3 | угловые камеры |
| `checker` | шахматная маска | равномерная сетка |
| `all` | всё окно | классический тоталистический рост |

Пороги `born`/`survive` — проценты от размера подмаски, поэтому правило
переносится между механизмами разного размера. Фазы: `grow` (200–400 шагов
без фильтров) и `hold` (40 шагов, фильтры каждый шаг).

* `filter.dynamics` — после прогрева карта меняется не более чем на 10% за шаг;
* `filter.density` — стен 30–75%;
* `filter.maze_structure` — связные проходы и равномерная плотность по плиткам;
* `filter.maze_graph` — графы: проходы одна связная компонента, средняя
  компонента стен ≥ 3 клеток, и почти нет одиночных «висящих» клеток ни у
  стен, ни у проходов.

Связная сеть стен с циклами обязательно разрезает проходы на карманы
(теорема Жордана на решётке), поэтому фильтр требует одновременно связности
проходов и отсутствия пыли, но не требует, чтобы все стены были одной
компонентой. На прогоне из 1200 случайных конфигов проходит около 4%.

## Восемь состояний в окне 5×5 (`omega5`)

Эксперимент `omega5` — большой, но полностью формализуемый автомат:
8 состояний (`0` — мёртвая клетка), окно видимости 5×5 (радиус 2 по
Чебышёву, 24 соседа) и правило, которое раскладывается на три слоя.

1. **Механизм счёта соседей** (`rule.omega5.mechanism`). Один скалярный
   счётчик строится по окну: вся маска, внутреннее/внешнее кольцо, четверти,
   8 направлений, крест, диагонали, строки/столбцы, шахматная маска, углы,
   число разных состояний, доминирующее/редкое состояние — 22 варианта.
2. **Категории рождения, выживания и смерти** (`rule.omega5.birth`,
   `survival`, `death`). Это интервалы по выбранному счётчику: «ровно 3»,
   «1–2», «2–4», «4–12», «не меньше половины» и т.п. Рождение переводит
   мёртвую клетку в `birth_state` (1…7), смерть — в `0`.
3. **Особая реакция** (`rule.omega5.trick`). Одно из 20 правил, нарушающих
   базовые пороги. Например, `stable6` всегда сохраняет состояние 6, а
   `predator4` заставляет 4 переходить в 2 и уничтожать все 3 в радиусе.
   Полный список — `sweep/experiments/omega5/rule.py`, словарь `TRICKS`.

Правило сериализуется без массивов: в конфиге лежат только строковые коды
механизма/категорий/реакции и числа. Из них собирается JSON-паспорт, который
показывается в галерее и печатается командой:

```bash
# паспорт правила для первого совместимого конфига
python -m sweep rule -e omega5

# паспорт конкретного успеха из прогона
python -m sweep rule --run-dir runs/omega5 --index 0

# сам перебор: пространство большое, удобнее random
python -m sweep run -e omega5 --strategy random --limit 2000 \
    --mode process --workers 4 --seed 1 --out runs/omega5

python -m sweep view --run-dir runs/omega5 --port 8000
```

В карточке браузера появляется блок «правило (JSON)»: механизм, интервалы
рождения/выживания/смерти, выбранная реакция и описание окна. Воспроизведение
идёт из того же конфига и `seed`, поэтому `view`, `viz`, `live` и `replay`
показывают один и тот же автомат. Если нужен собственный код в другом языке,
паспорт содержит `kernel: "omega5.v1"`, номера механизма и реакции — по ним
однозначно восстанавливается порядок вычислений.

## Плотные автоматы с выверенными долями (`omega5_dense`)

`omega5_dense` использует то же правило и окно 5×5, но ищет автоматы с
плотностью 65–85% (доля состояния `0` задаётся профилем, обычно 15–35%) и
выверенным составом остальных состояний. Параметры задаются профилем **до
запуска**.

Профиль лежит в `sweep/experiments/omega5_dense/profile.json`:

```json
{
  "density": [0.65, 0.85],
  "0": [0.15, 0.35],
  "1": [0.02, 0.05],
  "2": [0.02, 0.05],
  "3": [0.30, 0.50],
  "4": [0.05, 0.10],
  "5": [0.02, 0.05],
  "6": [0.02, 0.05],
  "7": [0.01, 0.05]
}
```

Профиль проверяется перед сборкой эксперимента:

* все 8 состояний должны быть заданы;
* `0 ≤ lo ≤ hi ≤ 1`;
* сумма минимумов ≤ 100% ≤ сумма максимумов — иначе доли физически не
  складываются в 100%;
* верхняя граница состояния `0` обычно не больше 35% (под плотность 65–85%);
* `density` задаёт границы `DensityFilter` (`min_fill`, `max_fill`).

Посмотреть и проверить профиль:

```bash
python -m sweep profile
python -m sweep profile --profile my_profile.json
```

Свой профиль можно передать в запуск напрямую:

```bash
python -m sweep run -e omega5_dense --profile my_profile.json \
    --strategy random --limit 2000 --mode process --workers 4 \
    --seed 1 --out runs/omega5_dense

python -m sweep view --run-dir runs/omega5_dense --port 8000
```

Отбор устроен так:

1. `warmup` — не вымереть и не стать слишком разреженным;
2. `observe` — на каждом шаге должно меняться 5–10% клеток, и
   изменения не должны сводиться к одному состоянию (проверяется по числу
   реально участвующих состояний/переходов);
3. `verify` — доля каждого состояния должна попасть в свой интервал, а в
   финальном кадре должно присутствовать достаточно разных состояний. Это
   отдельная фаза с нулевой длительностью, поэтому проверяется именно
   финальное состояние автомата.

Профиль попадает в конфиг обычными скалярными осями `dense.share<N>_lo/hi`.
Поэтому `successes.jsonl` остаётся самодостаточным рецептом: старый прогон
воспроизводится даже после правки `profile.json`. В галерее JSON-паспорт
правила дополнительно показывает блок `dense_profile`.

Для старта в профиле используется «плотная» инициализация
`randomizer.profile`: она раскладывает состояния по тем же долям, а не
заполняет сетку одним случайным состоянием. Это резко повышает шанс найти
автомат, который удерживает нужный состав, а не вымирает на первых шагах.

## Галерея и публикация

`python -m sweep view --runs runs --port 8000` открывает все прогоны сразу:
сверху переключатель эксперимента, снизу постраничная навигация (24/48/96/192
карточки), `←` и `→` листают страницы. Выбранный эксперимент, номер страницы
и размер страницы лежат в адресе (`?run=maze&page=3&size=48`), поэтому
перезагрузка возвращает на то же место. Поле «смещение» принимает номер
карточки или префикс `digest` и сразу открывает нужную страницу
(`?run=maze9&from=96&size=48`); номера карточек видны в их заголовках.

В карточке мета-параметры (`warmup`, `observe`, `seed`) и пункт `размер`
(32–192, кратно 16) пересобирают тот же автомат с другими длительностями фаз
или разрешением сетки; `×` меняет масштаб кадра, `fps` — скорость анимации.
Разрешение работает только для квадратных сеток: генерируется виртуальная ось
`grid2d.size`, которая ставит и `size`, и пару `width/height`.

Для GitHub Pages экспорт собирает каталог, который живёт без Python: страница
считает автоматы сама. Каждый эксперимент приносит браузерный модуль
`sweep/experiments/<имя>/web.js`, сборка склеивает ядро и модули в
`site/assets/rules.js`, а в `index.html` кладёт конфиг и две сжатые сетки
(затравку и итог) каждой карточки.

Готовый HTML в репозитории не хранится: он меняется целиком при каждой
сборке и весит около 8 МБ, поэтому собирается в отдельный каталог и уходит
артефактом в GitHub Actions. Сборка живёт в `pages/`:

```bash
pages/build.sh                 # соберёт pages/_site (каталог в .gitignore)
pages/build.sh /tmp/sweep-site # или в произвольный каталог
pages/build.sh /tmp/sweep-site --page-size 48 --title "sweep"
```

`pages/build.sh` — обёртка над `python -m sweep export --runs runs` (флаг
`--out`/`--run-dir` у команды `export` никуда не делся). Сборка печатает,
какие эксперименты вошли, а какие пропущены: у последних нет `web.js`, и
считать их кадры в браузере нечем.

Workflow `.github/workflows/pages.yml` запускается на push в `main`, если
изменились `sweep/`, `runs/` или `pages/`, собирает страницу в `$RUNNER_TEMP`
и публикует её через `upload-pages-artifact` + `deploy-pages`. Включается
один раз: Settings → Pages → Source: **GitHub Actions**. В git лежат только
исходники и `runs/*.jsonl`, поэтому история не растёт на мегабайты готовой
страницы (подробнее — `pages/README.md`).

В статической версии по умолчанию 24 карточки на странице (12/24/48), поле
«смещение» работает по номеру и по `digest`, а `▶` проигрывает рост заново
прямо в браузере. У каждой карточки есть одинаковый для всех экспериментов
набор контролов:

* `▶ / ⏸` — пуск и пауза;
* `↺` — вернуться к инициализации;
* `цикл` — после достижения цели начинать состояние заново;
* `размер` — инициализирующий размер сетки (ближайший сосед, 8–512);
* `итер.` — сколько итераций считать обзором;
* `итер/с` — сколько шагов автомата делать в секунду; `1` — один шаг в
  секунду, независимо от FPS отрисовки.

В шапке те же настройки можно применить ко всем карточкам сразу, а в
модальном окне `⛶` они дублируются для крупного просмотра. Анимация идёт
только у карточек в зоне видимости: уведите страницу вниз, и итерирование
останавливается. Итоговый кадр карточки взят из прогона, а «живой» прогон
считает браузерный модуль: у детерминированных правил (`langton`, `life`) он
совпадает клетка в клетку, у стохастических (`maze`, `maze9`) браузер
использует свой генератор, поэтому рисунок отличается от итогового кадра.

## Браузерный модуль эксперимента

Чтобы эксперимент попал в статическую галерею, рядом с его `__init__.py`
кладут `web.js` — маленький модуль без импортов и сборщика:

```js
registerExperiment({
  id: "maze9",                 // совпадает с именем Python-эксперимента
  label: "механизм в окне 9×9",
  create(card, env) { /* построить состояние по card.init */ },
  step(state, rng) { /* один шаг; меняет state.grid */ },
});
```

`create` получает карточку с распакованной затравкой и конфигом, `step` —
состояние и генератор для стохастических правил. Размер, число итераций,
скорость и цикл — не забота модуля: их реализует общий `Runner` из
`sweep/visualize/web/runtime.js`. Модуль описывает только само правило.

Слои web-сборки:

| файл | ответственность |
|---|---|
| `sweep/visualize/web/engine.js` | base64 ↔ сетка, ГПСЧ, палитра, окрестности, общие ядра `maze`/`omega5` |
| `sweep/visualize/web/runtime.js` | реестр экспериментов и `Runner` (размер, итерации, скорость, цикл) |
| `sweep/visualize/web/gallery.js` | карточки, страницы, контролы, модальное окно |
| `sweep/visualize/web/page.html` | разметка и стили |
| `sweep/experiments/<имя>/web.js` | только `create`/`step` эксперимента |

Контракт, helpers и чек-лист нового эксперимента подробно описаны в
[`sweep/visualize/web/README.md`](sweep/visualize/web/README.md). Сборка
проверяет `rules.js` и `gallery.js` через `node --check`, если node
установлен, и складывает карточки в `index.html` без единого запроса к
серверу.

## Свой эксперимент

```python
from numba import njit
from sweep.experiment import Experiment
from sweep.interfaces import CapabilityKind, Requirement, eq
from sweep.module import Role
from sweep.modules.data import Grid2D
from sweep.modules.filters import DensityFilter
from sweep.modules.neighborhoods import Moore
from sweep.modules.randomizers import UniformFill


@njit
def step(src, dst, zero, born):
    h, w = src.shape
    for y in range(h):
        for x in range(w):
            n = 0
            for dy in range(-1, 2):
                for dx in range(-1, 2):
                    if dy == 0 and dx == 0:
                        continue
                    n += src[(y + dy) % h, (x + dx) % w] != zero
            alive = src[y, x] != zero
            dst[y, x] = 1 if (n == born if not alive else 2 <= n <= 3) else zero


def build():
    e = Experiment("my_rule", "пример", stop_on_extinct=True)
    e.select(Role.DATA, Grid2D())
    e.select(Role.RANDOMIZER, UniformFill())
    e.select(Role.NEIGHBORHOOD, Moore())
    e.iterate(
        step,
        module_id="rule.my_rule",
        requires=(
            Requirement(CapabilityKind.GRID_2D),
            Requirement(CapabilityKind.ZERO_STATE),
            Requirement(CapabilityKind.NEIGHBORHOOD),
        ),
        declare=lambda ns, view: ns.range("born", 2, 5),
        bind=lambda fixed, view: (fixed["grid2d.zero"], fixed["rule.my_rule.born"]),
    )
    e.constrain(
        lambda v: v["grid2d.width"] * v["grid2d.height"] <= 96 * 96,
        ["grid2d.width", "grid2d.height"],
    )
    e.phase("warmup", e.range("phase.warmup", 0, 7, 3),
            filters=[DensityFilter(min_fill=0.01, max_fill=0.9)])
    e.phase("observe", e.range("phase.observe", 10, 31, 10),
            filters=[DensityFilter(min_fill=0.01, max_fill=0.9)],
            frequency="each")
    return e
```

Зарегистрируйте `build` в `sweep/experiments/__init__.py` и добавьте
визуализатор в `sweep/experiments/<name>/visualizer.py`.
