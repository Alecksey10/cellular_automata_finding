#### Число состояний

Правила итерации автомата могут конструироваться на основе области поиска, топологии, числа состояний. 
То есть я могу в любой момент при конфигурации задать произвольное число состояний, но из этого будет следовать то, что автомат поддерживает множественность состояний.
Таким образом, могут быть интерфейсы, которым автомат удовлетворяет, допустим:
* multi_states
    * details: 3 states
* если 2 состояния, то bi_states
* Если есть состояние,которое считается нулевым/мёртвым/пустым и т.д. - то ещё интерфейс corpse_state 

При этом, если какой-то из всевозможных модулей логики требует n состояний, например, модуль фильтрации требует, чтобы покрытие какой-нибудь из клеток было k%, тогда автомат должен обладать методом, который может вычислить это значение из любого автомата, удовлетворяющего интерфейсу "с нескольими состояниями". 

#### Топология

Автоматы могут быть как квадратными, так гексагональными, плотностными и т.д., за этим следует соответствие определённому интерфейсу.
* resolution
* dimenstion: 2d; 3d. (необязательно, чтоы у автомата был данный интерфейс, без него просто не будут работать некоторые модули)

#### Правила для перебора правил/логики работы автомата

* правила перебора логики работы
    * Примеры
        * Клетка выживает/рождается/умирает, если в [области поиска](#область-поиска) соответствующее число клеток. Автомат должен быть 2d, должен быть контекст предыдущей итерации, должна быть bi_state/multi_state{ states: 2}, хотя может работать на всех состояниях, для которых определён интерфейс corpse_state (то есть клетка будет)
        * Клетка выживает/рождается/умирает, если на определённых позициях соответствующее число клеток (несколько размытое правило)
        * Клетка выживает/рождается/умирает, если на определённых позициях соответствующее число определённых клеток (сильно размытое правило)
        * Случайный инициализитор подобного правил
    * и т.д.
* Правила перебора разрешения (автомат поддерживает интерфейс resolution; топологию 2d)
    * можно и resolution + 3d, но концептуально здесь речь идёт о том, что автомат поддерживает именно resolution с возможностью перебора.
    * Сам интерфейс для перебора будет перебирать разрешения, но с реализациями на несколько модулей, например
        * 2d_resolution_changer (перебирает от m до k с шагом ..., с рандомом, случайно и т.д.) 
        * 3d_resolution_changer (ожидает соответствие resolution и 3d)


* При этом правила переборов можно группировать, чередовать, условными

        * пред-предыдущее состояние. (это скользкий момент, это излишняя нагрузка на память, и, если того не требует автомат, чтобы эти данные никогда не хранились)

* хочу перебрать автомат, но число возможных состояний, допустим 10^125127, например, в случае с какими-нибудь много-соседными автоматами, тогда я:

3.2) перебор по числу соседей для жизни/смерти и т.д. 
3.3) В общем, эти параметры задаются извне, но по интерфейсу этой логики автомата, например, радиус смотрится от 1 до 3, для этого радиуса число соседей для рождения = (0 до радиус * радиус - 1). (то есть связанные параметры.) ... и т.д., то есть параметры завязаны друг на друге в рамках определённого модуля перебора логики. 
4) На каждой итерации проверка условия
5) сохраняю автомат


## Требования к организации кода
* Модули различных типов должны быть отдельны в отдельных файлах
* интерфейсы и соответствие им должно определяться явно, минимум непонятных строковых сравнений
* Построение автомата и его логики - это не один файл, а сборка всей логики через проверку соместимости модулей на основе представленной конфигурации теста. При этом носится динамический характер для перестроения автомата для следующего теста. 
## Требования иные

* обязательное ускорение кода, за счёт компиляции или чего-нибудь такого, многопоточность
* сам автомат может потребовать остановки (например, если логика автомата подразумевает работу только при существующих клетках, а если он выродился - то всё)
